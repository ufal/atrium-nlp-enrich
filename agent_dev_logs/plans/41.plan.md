## Context

A request whose UDPipe or NameTag call fails after its retries ends as `502 Pipeline produced no output (empty run, exit 1)`, exactly like an input that yields nothing. A LINDAT timeout ends there too, though the contract gives timeouts a 504 `limit_exceeded`. The exit code that would tell these apart is lost in two places:
- the clients exit 1 for everything;
- the stage scripts turn any failure into `exit 1`.

Everything after them (`run_pipeline.py`, `PipelineError`, the HTTP mapping) already passes a code through or maps it.

## Execution plan

### Phase A — the clients say why they stopped
1. Add a small module `api_util/exit_codes.py`:
   - `EXIT_EMPTY = 1`, `EXIT_MISSING_STAGE = 2` (documentation only; the runner owns that code);
   - `EXIT_UPSTREAM = 3`, `EXIT_UPSTREAM_TIMEOUT = 4`, `EXIT_TEITOK_CONTRACT = 5`;
   - a helper `classify_request_error(exc) -> int`: `requests.exceptions.Timeout` (including a urllib3 `MaxRetryError` whose reason is a read or connect timeout) → 4; any other `RequestException` → 3.
2. `call_udpipe.py:176-186`: exit with `classify_request_error(e)` and print one first line a person can read: `LINDAT UDPipe did not answer: <error>` (or `… timed out after <TIMEOUT> s × <retries>`). "No chunk files" and "all chunks empty" stay exit 1.
3. `call_nametag.py`: `call_nametag()` re-raises instead of returning `None` (or returns the exception). `main()` exits with the classified code and the same style of first line.

### Phase B — the stage scripts pass it on
4. In `api_2_udp.sh` and `api_3_nt.sh`, capture the client's code (`rc=$?` in the `else` branch, which `set -e` allows inside an `if`) and `exit "$rc"`, keeping the paradata `skip`. Its `--reason` names the cause for codes 3 and 4.
5. `chunk.py` failing stays exit 1: the input could not be split, so it is not an upstream failure.

### Phase C — the service maps them
6. `service/enrichment.py:609-631`:
   - `rc == 3` → `PipelineError(f"{first line}\n{tail}", 502)`; the first line is read from the tail (the client's `LINDAT …` line), so the detail starts with the cause;
   - `rc == 4` → raise `atrium_limits.LimitExceeded("lindat_timeout_s", <value>, None, unit="s", env="LINDAT_TIMEOUT_S", http_status=504, detail=…)`, the same type `API_JOB_TIMEOUT` already raises (`service/api.py:781`), so the error body and `/jobs` reason come out the same;
   - 1 stays "empty run".
7. `/jobs` (`service/api.py:776-790`): a 504 from rc 4 lands in the existing `LimitExceeded` branch (`job.reason = "limit_exceeded"`).

### Phase D — tests and docs
8. Tests (no network):
   - `tests/test_lindat_failures.py`: a stub HTTP server on `127.0.0.1` (the pattern `tests/test_backing_service_urls.py` uses) that sleeps past a 1 s `--timeout` or answers 503. `call_udpipe.main()` and `call_nametag.main()` exit 4 and 3 with the `LINDAT …` first line.
   - The stage script gets one bash-level test with a stubbed client (`run_pipeline.py` already has subprocess fixtures in `tests/test_run_pipeline.py`).
   - Extend `tests/test_api_service.py:81-96` with rc 3 → 502 (detail starts `LINDAT`) and rc 4 → 504 `limit_exceeded`, `limit == "lindat_timeout_s"`. An empty-input run stays 502 "empty run".
9. Docs:
   - `service/README.md:275-279` (the exit-code map), the 502/504 rows of the error table (`:363-365`), and the `lindat_timeout_s` row (`:340`): "→ 504 `limit_exceeded` once the retries are spent".
   - A line in `CONTRIBUTING.md`'s release history with the next release; DEVLOG.

## Verification

- `atrium_openapi.py check`: the spec does not change (statuses and descriptions already exist), so the API Meta-Contract job stays green.

  - an empty CSV → 422 before any stage runs (`_check_rows`); a run whose stages all skip → 502 "empty run".

## Open questions

- Should a 504 count the retries in its detail (`60 s × 6 attempts`)? Proposed: yes. The total wait, not the per-call limit, is what a client sizes its own timeout by.

## Out of scope

- A new reason code for upstream failures: a hub `atrium_service.py` change for all six services; not needed while `reason: null` plus a detail is enough.
- Retrying inside the service on 3 or 4: the client retries, per the contract.
