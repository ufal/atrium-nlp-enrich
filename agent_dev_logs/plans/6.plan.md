## 0. Governing principles

Everything below is subordinate to three rulings. When a task here conflicts with one of them, the ruling wins.

**P1 — Apply, don't reorganise.** AMCR and TEATER remain authoritative in how their terms are organised and interpreted. Nothing in this workstream constitutes a change to either source vocabulary. Any actual change to AMCR needs a dedicated decision process outside this issue.

**P2 — Facets are plumbing.** They organise and prioritise the prompt. They are not semantic output and not a new taxonomy. Keep "which terms are available to the model" strictly separate from "how those terms are grouped for inference" — including in how the code, the config, and the output schema are structured.

**P3 — Keep by default; exclude on evidence.** A TEATER branch comes out only when enrichment results show it is irrelevant or introduces systematic, otherwise unsolvable noise. Purely technical/administrative AMCR lists are the standing exception.

## 3. Workstream B — Dedup and term identity — ✅ **done in `a5e3c8a`**

This was where most of the actual code work sat. All of it landed; what follows records what each item turned into, because two of them turned into something different from what was planned.

### B1 — Same-label grouping (finding 1) — ✅ done, **not as specified**

The plan said "key dedup on `cs` + `en`". Implemented instead as: group by `cs`, and treat the whole group as **one concept unless an override says otherwise** (B3/B4).

The reason is in the data. A `cs`+`en` key silently declares "different gloss ⇒ different concept", and against the real harvest that is wrong far more often than it is right:

| Label            | Glosses across its records                                 | Reality          |
|------------------|------------------------------------------------------------|------------------|
| `přírodní útvar` | *natural landform* (×2, AMCR) / *natural feature* (TEATER) | one concept      |
| `cesta`          | *roads* / *path/road* / *path*                             | one concept      |
| `olej`           | *oil* / *oils*                                             | one concept      |
| `pevnost`        | *fortress* / *fort*                                        | one concept      |
| `zámek`          | *lock* (×2) / *châteaux*                                   | **two concepts** |

Auto-keying on `cs`+`en` would have produced a bracketed split for every row above, not just the last one — inventing homonyms out of translation variance, which is exactly the judgement M10 assigns to @david-spacil. So the key stayed `cs`, the winner is still the lowest record in canonical order, and the difference from before is that the losers are no longer *discarded* — they are recorded (B2). Where a split is genuinely wanted, an override makes it (B3).

Consequence for the 16 role-differing collisions (`budova`): unchanged and expected — they need a human verdict, and now there is a place to put one.

Within-source scale confirmed on the real data: AMCR's double registrations (`kostel` HES-000021/HES-000465 etc.) are all kept as ids on the survivor.

### B2 — Carry all discarded ids on the surviving term (M7) — ✅ done as specified

- **Vocabulary file:** each term gained `discarded_ids` — `{source, id, scheme, cs, en}` per absorbed record. On the current build: 583 records across 470 terms.
- **Prompt:** unchanged. Ids are not serialised into the system prompt.
- **Output:** `teater_category_ids` is attached after inference in `llm_run.main()`, as `[{source, id}, …]` covering the surviving record **plus** everything it absorbed, so a consumer never has to open the vocabulary file to reconstruct the set. `teater_category` keeps its existing string shape.
- **Reversibility:** behind `EMIT_CATEGORY_IDS` (default `true`) in `llm_config.txt`, per M7's "drop it if it will create some issues".

Implementation note: the attach step lives in `llm_run.main()`, not inside `process_document`/`process_document_vllm`. Both backends funnel through one list, so this is one insertion point instead of two, and the inference loop stays ignorant of vocabulary internals.

### B3 — Bracketed qualifiers for genuine homonyms (M8) — ✅ mechanism done, review outstanding

- **Trigger:** an explicit `qualifier_cs` entry in `taxonomy_overrides.json`. Never inferred (see B1).
- **Qualifier source:** the record's own sub-branch label, as the plan proposed — TEATER 1439's own sub-branch is `sídlo elity`, giving `zámek (sídlo elity)`.
- **Effect:** the flagged record is pulled out of the dedup group into its own enum entry; the rest of the group still resolves to the bare label. `zámek` → `Artefact` (AMCR HES-000817, absorbing TEATER 2358) and `zámek (sídlo elity)` → `Activity Area` (TEATER 1439). Both senses are now reachable.
- **Prompt-only:** the entry carries `bare_cs`, and `llm_run` strips the qualifier from the emitted `teater_category` by **exact map lookup, not a regex**. This matters: 319 terms legitimately contain parentheses (`GPS (navigační systém)`), and a trailing-parenthesis regex would have mangled every one of them — and mangling a source-authored label would breach P1.
- **Review load:** unchanged at 139 differing-gloss rows (28 already covered). Each verdict is now one entry in `taxonomy_overrides.json`; no code change per verdict.

### B4 — Per-term overrides — `taxonomy_overrides.json` (O5, finding 4) — ✅ done

Shipped close to the proposed shape, with one correction: overrides are applied **before** `heslar_map`/`teater_branch_map`, not after. An override exists to beat the list rule, so it has to be checked first.

```jsonc
{
  "overrides": [
    { "match": { "source": "amcr", "id": "HES-000021" },
```

Matching is on `(source, id)` only — never the bare label, which is the ambiguity being fixed. `validate_settings()` now rejects an override naming an undeclared facet, exactly as it already did for the two maps, and the audit CSV records `override:<source>:<id>`. ## 5. Workstream D — Evaluation criteria *(critical path)*

Nothing downstream produces a trustworthy number until this exists. It is also the one item neither reviewer has moved on since 11 August — and with A/B/C now built, **it is the only thing left blocking E.** Everything else in this plan is either done or waiting on one question to @motyc.

Two items below became concrete rather than hypothetical in `a5e3c8a`: `teater_category_ids` now exists, so D3's "traceable to the exact term set it saw" is achievable per record and not just per run; and the qualifier mechanism means a scored answer may legitimately arrive as `zámek` with a specific id attached, so the rubric needs to say whether the id participates in scoring or only the label does.

**D1 — Write the gold-label rubric before annotating anything.** Answer, in the issue, so the answers are citable:
- Are form labels (`OBEC`, `ČÍSLO PARCELY`, `Druh nálezu`) meta-text? *(Proposed: yes — a field name is not content.)*
- Is a correct-but-less-specific term wrong, or partially credited? *(Proposed: partial credit, tracked separately, since the prompt actively instructs specificity — full-credit-only makes the metric insensitive to exactly the behaviour being asked for.)*
- Are `extracted_keywords_cs/en` scored, or only `teater_category`? *(Proposed: both, reported separately — the keyword array is what actually reaches an index.)*
- **New, from B3/F:** when two vocabulary entries are legitimately both correct for a line (`most` vs `most/brod`), both count as correct. This must be in the rubric before scoring, or the composite-label problem is scored as model error.
- **New, from A1a:** how a geographic/ethnic selection is scored, so the guardrail decision is measurable rather than assumed.

**D2 — Fix the sample.** ~14 cited lines out of 618 × 8 is anecdote-adjacent, and the verdicts demonstrably flip on line choice (`qwen3_14b` on the second "Druh nálezu", `CTX196006127_1_25`). Pick a fixed line set, score *every* line in it, publish per-model confusion against the gold labels.

**D3 — Paradata beside every output set.** `atrium_paradata.py` already writes run records; the eight shipped sets have none, which is why "do these come from the same commit?" was unanswerable. Make the sidecar mandatory, and include the vocabulary artifact's identity (path + `meta.json` sha) so a run is traceable to the exact term set it saw.

## 7. Workstream F — The open question we were handed

**F — Two different labels meaning the same thing.** `zámek/zámeček/vila` vs `zámek`, `most/brod` vs `most`, `budova/stavba`, `muzeum/skanzen` — 15 pairs where AMCR packs related concepts into one entry and a component also exists standalone, so the concept is offered twice, in two facets. @motyc: *"Not sure. Please try to come up with solution while looking into data."*

**Unchanged by `a5e3c8a`, by construction.** These pairs are *distinct strings* (`most` and `most/brod` never collide), so they never enter a dedup group and none of B1–B5 touches them. The work done does, however, supply two of the pieces the proposal below needs: `discarded_ids` establishes the precedent and the shape for recording record-level relations in the vocabulary file, and `taxonomy_overrides.json` establishes where a hand-made, reasoned, per-record assertion lives.

Proposed approach, to be validated against E3 rather than asserted:

1. **Keep both, link them.** Under P1, dropping an AMCR label is a change to AMCR's own content — precisely what the principle forbids. Instead add an equivalence relation (`same_as`, keyed on `(source, id)` pairs) in the vocabulary file, populated for the 15 pairs — structurally the same move as `discarded_ids`, but asserting "equivalent to" rather than "absorbed".
2. **Let the equivalence do the work at scoring time**, not at prompt time: both entries stay selectable, and D1 counts either as correct. This makes the ambiguity harmless where it actually causes damage — in the metric.
3. **Optionally prefer one at prompt time**, if E3 shows the duplication measurably splits model attention. That is an evidence-driven, reversible tuning decision rather than a vocabulary edit — consistent with P1 and P3.
4. Report the finding back to @motyc with E3's numbers attached, since he asked for a data-informed answer rather than a judgement call.
