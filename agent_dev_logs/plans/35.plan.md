default every service to `replicas: 1`, with a comment saying which services may raise it.

mirror is a squashed re-import, so *at or before* that commit is the strongest honest statement, and it is two
days before #35 was opened on 2026-09-10 12:24.

So the question has changed. It is no longer *"what do we design?"* It is **"what single unmet acceptance

## Strategic actions

### A — Write the runbook paragraph. This is the issue.

Everything else on this page is optional. `docs/k8s_acceptance_runbook.md` in the **hub** is the one file that
stands between #35 and closed, and it is one paragraph.

Place it where the partner meets the constraint, not in an appendix. Two workable slots:

1. **As a fourth item in `## Before you start`** (the section runs `:14-31`; the `ALLOWED_ORIGINS` item sits at
   `:29-31`). This section already carries exactly this kind of trap — item 2 at `:23-28` is the nlp-enrich
   upload-limit collision, written in the same voice. A fourth item beside it is the lowest-friction fit.
2. **Inline beside the apply step** at `:36-38`, where the reader runs
   `sed -e 's/<tool>/nlp-enrich/g' … | kubectl apply -f -`.

Content it must carry, all of which already exists in `docs/k8s_deployment.md:233-238` and can be compressed:

- the manifest's `replicas: 1` is deliberate and is the safe default, not an oversight to be tuned away;
- raising it is safe for translator, page-classification, alto-postprocess and llm-enrich;
- raising it for **nlp-enrich** breaks `GET /jobs/{id}`, because the job registry is in-memory per process — a
  poll can land on a different replica and reads as **404**, not "still running";
- so the `/jobs` smoke request at `:122` is only meaningful at one replica.

Cross-link it to `docs/k8s_deployment.md` §"Known limits" (`:212`) rather than restating the whole note. Also
worth a `Notes` hint in the results-log row at `:132`, which is where a partner records what they actually ran.

**This is a hub commit.** Nothing in this repo has to change for the issue's acceptance to be met.

### B — The optional guardrails (the previous plan's §C), unchanged and still unmet

Not required by the acceptance, cheap, and the only way the constraint becomes discoverable from a **running
system** instead of from a document. Nobody reads a manifest comment at 2am.

- **Say it in the API surface.** `service/api.py:524`, `:532` and `:543` all raise a bare `"Job not found"`.
  Returning 404 for an unknown id is correct HTTP and useless diagnostically. Add to the detail that job ids
  are local to the serving instance, so an operator seeing an intermittent 404 has the answer in their hands.
  Keep the status code and the existing `from None`; this is a detail-string change at three sites.
- **Say it at startup.** One `INFO` line in `service/api.py`'s lifespan (around the `_state.warm = True` at
  `:62`) noting that `/jobs` state is process-local and the service expects a single replica. It lands in the
  log a partner reads when something is already wrong.
- **Say it in the variable table.** `service/README.md:196` — `API_KEEP_WORKSPACES`'s row should say a kept
  workspace survives only as long as the pod, since `_API_JOBS_ROOT` (`service/enrichment.py:42`) is
  container-local disk and the `shutil.rmtree` guards at `:451-452`, `:563-564` and `:683-685` are the only
  thing standing between a kept workspace and a pod restart that takes it anyway.

Take these together or not at all — they are one small commit in this repo, and they close the oddity that the
repo which *owns* the constraint is the only place in the ecosystem that never mentions it.

### C — Record the standing decision, and reframe it as "revisit?" rather than "choose?"

The issue offers two resolutions and declines to pick. **The manifest has in effect already picked.**
Shipping `replicas: 1` as the safe default with a documented exception *is* option 1 ("cheap: document the
constraint"), and it has been the deployed reality since at or before 2026-09-08. The open question is not
which option to take; it is whether anyone wants to **revisit** that choice.

The reasoning for leaving it alone, recorded so it reads as a decision rather than as the cheap way out:

- The project is in a pre-closure architecture review with a fixed remaining lifetime and a partner handover
  as the live deliverable.
- Option 2 ("correct": move the registry and workspace root to shared state) means introducing a shared store
  or a `ReadWriteMany` volume into a deployment ARÚP/ARÚB have not yet accepted — new infrastructure, new
  failure modes, new acceptance surface, to enable a scale-out nobody has asked for.
- `docs/k8s_acceptance_runbook.md` never asks for more than one replica of anything.
- Option 2 also lands directly on the `_state.track()` registration at `service/api.py:516` that acceptance
  bullet 3 forbids regressing — a replica draining must not abandon a job another replica could report on.

Option 2 is the better system and the wrong project stage. Say that on the thread, with the file:line evidence
that the constraint is already documented in two of three places, so a future maintainer knows exactly what to
revisit if the service outlives the project — and so the issue stops reading as an unmade decision.

**Post this as a comment.** The thread has had **0 comments since 2026-09-10** and still asserts *"nothing
says so"*, which has not been true since before the issue was filed. Closing #35 silently would leave that
assertion as the last word.

### D — Do not regress #55, and do not re-derive option 2

`service/api.py:516` registers the background job with `_state.track()`, which `serve_lifecycle(_state)`
(`:69`) awaits on shutdown — the fix for #55's "a rolling restart kills in-flight work". Under actions A–C
nothing here changes; keep it that way. Note that grepping `tests/` for `.track(` returns nothing, so this
registration is guarded by the comment at `:509-515` and by the drain-state tests in
`tests/test_api_contract.py` (`:117`, `:141`), not by a test of its own — a small gap worth knowing about, but
not one #35 has to close.

If option 2 is ever revisited: the registry moves behind an interface with a shared-store implementation (the
`asyncio.Lock` at `service/jobs.py:20` becomes meaningless and must not be relied on for cross-replica mutual
exclusion), `API_JOBS_ROOT` (`service/enrichment.py:42`) moves to a `ReadWriteMany` volume, and
`ServiceState.track()`'s drain semantics need re-examination. That is a substantially larger change with new
infrastructure in the partner's cluster, and it should be its own issue, not a variant of this one.

## Out of scope

- **Re-designing the manifest's replica mechanism.** Done, at or before 2026-09-08. The previous edition's §B
  enumerated three options and recommended the one already in the file.
- **The other four services.** Verified stateless; no change. (Line numbers corrected in the snapshot above.)
- **`--workers` / in-process concurrency.** The replica model is correct and this issue does not revisit it.
  `keywords.py:678`'s `--workers` is batch process-pool parallelism inside one container, not an HTTP worker
  count, and is out of scope for factor VIII.
- **What `processing.log` is for** — [ufal/atrium-project#61](https://github.com/ufal/atrium-project/issues/61).
  Its D3 relay landed on 2026-09-12 at `service/enrichment.py:306-348` without waiting on this issue and
  without touching workspace lifetime; #61's own digest records that it "still owns the disk half of D3".
  The two were separable, as this pair predicted.
- **Job persistence across restarts.** A registry that survives a pod restart is a different feature from one
  shared between replicas. Neither is being added here, and `docs/k8s_deployment.md:226-232` already tells the
  partner not to expect the former.
