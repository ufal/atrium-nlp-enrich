# Strategy — Issue #35: state or remove the single-replica constraint for `/jobs`

> Issue [\#35](https://github.com/ufal/atrium-nlp-enrich/issues/35) · Labels: `enhancement`, `development` · Parent: [atrium-project#53](https://github.com/ufal/atrium-project/issues/53) (factors VI + VIII)
> **Status: 🟡 Not started. The code finding is settled; what is open is a decision, and a mechanism for expressing it in a uniform manifest. Evidence in [`../digests/35.digest.md`](../digests/35.digest.md).**

## Context

This is the ecosystem's only stateful service. `service/jobs.py:19` holds the job registry in a process-local dict; `service/enrichment.py:39` writes workspaces to container-local disk under `API_JOBS_ROOT`. `GET /jobs/{id}` therefore resolves only on the replica that accepted the `POST`.

That is a defensible design for an async job API. What is not defensible is that `docs/templates/k8s/atrium-service.deployment.yaml` — the uniform manifest ARÚP/ARÚB deploy all five services from, per `docs/k8s_acceptance_runbook.md` — carries one replica policy for all of them and says nothing about this. A partner who scales up gets intermittent 404s on jobs that are running fine, with nothing in the logs or the docs pointing at the replica count.

The issue frames two resolutions and does not choose. This plan chooses, and then addresses the part neither the issue nor #53 has worked out: **how a uniform, `sed`-substituted manifest expresses a per-tool exception.**

## Strategic actions

### A — Choose option 1 (document the constraint), and say so on the issue

**Recommendation: option 1.** The project is in a pre-closure architecture review with a fixed remaining lifetime and a partner handover as the live deliverable. Moving the registry and workspaces to shared state means introducing a shared store or a `ReadWriteMany` volume into a deployment ARÚP/ARÚB have not yet accepted — new infrastructure, new failure modes, and new acceptance surface, to enable a scale-out nobody has asked for.

Option 2 is the better system and the wrong project stage. Record the reasoning on the issue so it reads as a decision rather than as the cheap way out, and so a future maintainer knows what to revisit if the service outlives the project.

The bar for "documented" is that the constraint appears everywhere a partner could learn it too late:

1. the manifest, as an explicit `replicas: 1` with a comment saying why;
2. `docs/k8s_deployment.md`, in prose, near the scaling guidance;
3. `docs/k8s_acceptance_runbook.md`, so it is visible during the acceptance round rather than after.

All three files are in the **hub** repository. Closing this issue takes commits in two repos.

### B — Solve the uniform-manifest problem (the real work)

`atrium-service.deployment.yaml` is substituted with `sed -e 's/<tool>/nlp-enrich/g' -e 's/<version>/…/g'`. It has no conditionals. A per-tool `replicas` value cannot be expressed by substitution alone. Three options:

1. **Default `replicas: 1` for every service, with a comment saying which services may raise it.** Simplest, safest, and honest: nothing in the acceptance runbook requires more than one replica, and a partner raising it for the four stateless services is doing so deliberately, having read the comment. **Recommended.**
2. **A documented override step in the runbook** — apply the manifest, then `kubectl scale`. Puts the constraint in a procedure that can be skipped.
3. **A second template for nlp-enrich.** Duplicates a file that six repos' docs point at, and creates exactly the parallel-enumeration drift problem [atrium-project#59](https://github.com/ufal/atrium-project/issues/59) exists to fix.

Option 1 also has the virtue that it makes the *safe* configuration the default and the risky one opt-in, which is the right way round for a handover.

### C — Make the constraint visible from inside the service, not only in docs

Documentation is the resolution, but it is the weakest kind of guardrail — nobody reads the manifest comment at 2am. Two cheap additions, both local to this repo:

- **Say it in the API surface.** `GET /jobs/{id}` returning 404 for an unknown id is correct HTTP and useless diagnostically. Include in the 404 body that job ids are local to the serving instance, so an operator seeing an intermittent 404 has the answer in their hands.
- **Say it at startup.** One `INFO` line at boot noting that `/jobs` state is process-local and the service expects a single replica. It costs nothing and it lands in the log a partner will actually read when something is wrong.

Neither replaces §A. Both mean the constraint is discoverable from a running system, not only from a document.

### D — Do not regress #55

`POST /jobs` registers with `ServiceState.track()`, which the graceful-shutdown drain awaits — that registration is the fix for #55's "a rolling restart kills in-flight work", and it was verified against a real uvicorn subprocess sent a real SIGTERM.

Under option 1 nothing here changes; keep it that way and re-run the check. Under option 2 it would be directly in the blast radius, which is a further argument for option 1.

## Verification / done-criteria

- [ ] The manifest sets `replicas` explicitly, with a comment naming the constraint and this issue.
- [ ] `docs/k8s_deployment.md` states nlp-enrich's replica constraint in prose.
- [ ] `docs/k8s_acceptance_runbook.md` surfaces it during the acceptance procedure, not after.
- [ ] The 404 body and the startup line from §C exist, and an operator can reach the explanation without reading the manifest.
- [ ] **The failure is reproduced before and absent after**: run two instances behind anything round-robin, `POST /jobs` to one, `GET /jobs/{id}` repeatedly, and observe the intermittent 404 today. After the fix, either the deployment cannot produce two replicas, or the 404 explains itself. Do not accept "we wrote it down" without having seen the failure it describes.
- [ ] #55's drain still holds: SIGTERM a container with an in-flight job and confirm the job completes.
- [ ] `API_KEEP_WORKSPACES`'s documented meaning reflects that kept workspaces live only as long as the pod.

## If option 2 is chosen instead

Recorded so the alternative is not re-derived from scratch: the registry moves behind an interface with a shared-store implementation (the `asyncio.Lock` at `service/jobs.py:20` becomes meaningless and must not be relied on for cross-replica mutual exclusion), `API_JOBS_ROOT` moves to a `ReadWriteMany` volume, and `ServiceState.track()`'s drain semantics need re-examination — a replica draining must not abandon a job another replica could report on. That is a substantially larger change with new infrastructure in the partner's cluster, and it should be its own issue, not a variant of this one.

## Out of scope

- **The other four services.** Verified stateless; no change.
- **`--workers` / in-process concurrency.** The replica model is correct; this issue does not revisit it.
- **What `processing.log` is for** — [atrium-project#61](https://github.com/ufal/atrium-project/issues/61). This issue decides `/jobs`'s promise; that one follows from it.
- **Job persistence across restarts.** A job registry that survives a pod restart is a different feature from one shared between replicas. Neither is being added here.
