**Status**: 🆕 **Open — designed, not started.** Nothing moved in the code since 10-08. Decisions 1–3 (digest) are K4TEL's, and phase A waits on them.

## Context

A born-digital document has no ALTO, and flexiconv is off the production chain, so its TEITOK today is text only: `<pb>`/`<lb>` without coordinates and no `<surface>`. Its record, written by digital-convert, already carries `pages[].canvas` and `lines[].bbox` in TEITOK's convention (top-left origin, y down). It also reaches stage 4 as the run's baseline. The work is an adapter, not a second writer: read the record into the structure `_parse_alto()` returns, and let alignment, page resolution and the writer run unchanged.

## Execution plan

### Phase A — the adapter
1. **New `api_util/record_layout.py`: `parse_record_layout(path_or_record)`.** It returns `(strings, pages, graphics, blocks, meta)`:
   - **pages:** one per `pages[]` entry with a canvas: `{id: f"pg_{page_index}", width, height, idx: page_index, ps_*: 0}`.
   - **blocks:** from `lines[].group_id` when present; a block's box is the union of its lines.
   - **strings:** each line's text, split on whitespace. Each word gets a box (decision 1) and carries:
     - `line_id = f"l{page}.{line}"`;
     - `line_bbox` (the line's own box);
     - `block_id`;
     - `lang` (the line's `lang`, when ocr-postprocess scored it).
   - **graphics:** none.
   - **meta:** `measurement_unit` = the canvas unit; `layout_source = "record"`; the converter's name and version from the record's provenance, for the header.
2. **Lines and pages without geometry.** Lines without a `bbox`, and pages without a canvas (a DOCX record), give no strings. The rows file then places their tokens, as today.
3. **`bbox_scale.unit_per_inch`:** add `"pt": 72.0` (decision 2), so `IMAGE_DPI` converts points to pixels. Page images rendered from the PDF (`INPUT_PAGES_DIR`) are already matched by tier 1. Without either, boxes stay in points under the existing warning, reworded for a record ("set IMAGE_DPI to the DPI the page images will be rendered at").

### Phase B — the third layout source
4. `api_util/doc_identity.py:95` `layout_source()`: after ALTO and the converted TEITOK, return the baseline record when it has at least one page with a canvas and one line with a bbox. A helper `record_has_geometry(path)` keeps the check cheap: one JSON read, no schema validation.
5. `teitok_alto._parse_alto()` (`:352`): dispatch a `.document.json` path, or a JSON whose `record_type` is `atrium-document` or `atrium-document-merged`, to `parse_record_layout()`, next to the TEI dispatch (`:372-379`).
6. `summarize_nt_udp.py:616`: pass `document_json_dir` into `layout_source()`, so the record is found before `write_teitok_merged()` runs. The service reaches the same directory through `run_pipeline.py:342-388`.
7. **The header.** The `<teiHeader>` names the record (`doc_id`, `source.filename`) and the converter as the layout's origin, as `teitok_layout.py` names flexiconv. Approximate word boxes are declared there.

### Phase C — the service and the spec
8. `service/enrichment.py:703`: `layout_source` is `"record"` when no layout was uploaded and stage 4 used the record. Stage 4 writes the source it used into its paradata `statistics` (`layout_source`), and the service reads it there instead of guessing from the request.
9. `service/api.py:175` and `service/openapi.json:2517`: "`alto`, `teitok`, `record` or `rows`". `atrium_openapi.py check` must show only that additive change.
10. **The record is never written back.** On a digital-born record, `lines[].bbox` belongs to digital-convert (schema `:282`). `document_hook.py:382-392` keeps the `lines[]` merge off. Add a comment there: whoever enables it must skip `bbox` when `source.origin` is digital-born.

### Phase D — tests and docs
11. **Fixture, synthetic only.** Build a two-page, two-column record from digital-convert's `tests/fixtures/digital/make_fixtures.py` `two_column_pdf()` through `api_util/digital_to_json.py`. Commit it with its text table under `tests/fixtures/record_layout/`.
    - Do not copy a record from digital-convert `data_samples/records/`. Those records hold real AMČR text, and their public status is open on atrium-project#16.
12. **`tests/test_record_layout.py`:**
    - the adapter's 5-tuple matches the record (pages, line boxes, word boxes inside their line box);
    - `pt` at `IMAGE_DPI=144` doubles the coordinates;
    - a record without a canvas yields no strings;
    - `write_teitok_merged()` with the record writes one `<surface>` per page and boxed `<lb>` and `<tok>`, and passes `validate_teitok_xml.py` and the XSD (the helpers of `tests/test_teitok_conformance.py`).
13. **The service.** Three cases with the fixture's text table:
    - with `document_json`: `layout_source: "record"`;
    - without it: `rows`;
    - with an `alto` part as well: `alto` (an upload wins).
14. **Docs:**
    - `service/README.md` "Layout inputs" (`:57`) and its `layout_source` line (`:151`): the record as the third source; units and `IMAGE_DPI`; approximate token boxes; DOCX without boxes;
    - `teitok_conformance_plan.md` Stage 8 marked done;
    - the CONTRIBUTING release row and the DEVLOG.

## Done-criteria
As in the digest: a PDF record gives a boxed TEITOK and `layout_source: "record"`; conformance and XSD pass; `entities[].bbox` comes from token boxes; DOCX keeps rows; the README lists the record.

## Open questions
- Decisions 1–3 (digest).
- Should `/enrich` take the record as its only input, deriving the text table from `lines[]`, so a client need not build the CSV? That is a small change to `_normalize()`, worth its own issue once W5 works.

## Out of scope
- **Word-level boxes from digital-convert.** The record schema has no word level. Exporting pdfplumber's word boxes would be a hub schema change.
- **Page images for born-digital PDFs:** the client renders them, or page-classification does. `INPUT_PAGES_DIR` already consumes them.
