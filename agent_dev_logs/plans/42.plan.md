## Context

A born-digital document has no ALTO, and flexiconv is off the production chain, so its TEITOK today is text-only: `<pb>`/`<lb>` without coordinates, no `<surface>`. Its record, written by digital-convert, already carries `pages[].canvas` and `lines[].bbox` in the coordinate convention TEITOK uses (top-left origin, y down). The record also already reaches stage 4 as the run's baseline (`{document_json_dir}/{doc}.document.json`). The work is an adapter, not a second writer: read the record into the structure `_parse_alto()` returns, and let alignment, page resolution and the writer run unchanged.

## Execution plan

### Phase A — the adapter
1. **New `api_util/record_layout.py`: `parse_record_layout(path_or_record)`.** It returns `(strings, pages, graphics, blocks, meta)`:
   - **pages:** one per `pages[]` entry with a canvas, `{id: f"pg_{page_index}", width, height, idx: page_index, ps_*: 0}`.
   - **blocks:** from `lines[].group_id`, when present (block box = union of its lines).
   - **strings:** each line's text split on whitespace. Each word gets a box apportioned along the line box by character offset (decision 1a), and carries `line_id = f"l{page}.{line}"`, `line_bbox` (the line's own box), `block_id` and `lang` (the line's `lang`, when ocr-postprocess scored it).
   - **graphics:** none.
   - **meta:** `measurement_unit` = the canvas unit, `layout_source = "record"`, and the converter's name and version from the record's provenance (`source`, the digital-convert stamp) for the header.
2. Lines without a `bbox`, or pages without a canvas (a DOCX record), give no strings for those pages. The rows file then places their tokens, as today.
3. **`bbox_scale.unit_per_inch`:** add `"pt": 72.0`, so tier 2 (`IMAGE_DPI`) converts points to pixels. Tier 1 (page images rendered from the PDF, `INPUT_PAGES_DIR`) already scales to the image. Without either, boxes stay in points under the existing warning, reworded for a record ("set IMAGE_DPI to the DPI the page images will be rendered at").

### Phase B — the third layout source
4. `api_util/doc_identity.py::layout_source()`: after ALTO and the converted TEITOK, return the baseline record path when it has at least one page with a canvas and one line with a bbox. A helper `record_has_geometry(path)` keeps that cheap: it reads the JSON once, with no schema validation.
5. `teitok_alto._parse_alto()`: dispatch on a `.document.json` path, or on a JSON whose `record_type` is `atrium-document`, to `parse_record_layout()`, next to the existing TEI dispatch.
6. `summarize_nt_udp.py:616`: pass `document_json_dir` into `layout_source()`, so the record is found before `write_teitok_merged()` runs.
7. **Header:** the `<teiHeader>` names the record (doc_id, `source.filename`) and the converter as the layout's origin, the way `teitok_layout.py` names flexiconv. The word boxes are declared approximate, with an `appInfo` note or `@resp` on the surface.

### Phase C — the service and the spec
8. `service/enrichment.py:653`: `layout_source` becomes `"record"` when no layout was uploaded and stage 4 used the record. The stage writes the source it used into its paradata `statistics` (`layout_source`), so the service reads it there instead of guessing from the request.
9. `service/openapi.json` and the `EnrichResponse` field description (`service/api.py:175`): "`alto`, `teitok`, `record` or `rows`". `atrium_openapi.py check` must show only that additive change.
10. **The record is never written back.** On a digital-born record `lines[].bbox` belongs to digital-convert (schema: two writers, exclusive by `source.origin`). Check that `document_hook.py` (`:389-392`, the `lines[]` grant) leaves it alone.

### Phase D — tests and docs
11. **Fixture.** A small born-digital record (two pages, two columns), generated once from digital-convert's `tests/fixtures/digital/make_fixtures.py` (`two_column.pdf`) through `api_util/digital_to_json.py`, and committed with its text table under `tests/fixtures/record_layout/`.
12. **`tests/test_record_layout.py`:**
    - the adapter's 5-tuple matches the record (pages, line boxes, words apportioned within their line box);
    - `pt` scaling at `IMAGE_DPI=144` doubles the coordinates;
    - a DOCX-like record (no canvas) yields no strings;
    - `write_teitok_merged()` with the record writes one `<surface>` per page, boxed `<lb>` and `<tok>`, and passes `validate_teitok_xml.py` and the XSD (`tests/test_teitok_conformance.py`'s helpers).
13. **The service.** `/enrich` with the fixture's text table and `document_json` answers `layout_source: "record"`; without `document_json`, `rows`; with an `alto` part as well, `alto` (an upload wins).
14. **Docs.**
    - `service/README.md` "Layout inputs" (`:57`): the record as the third source; units and `IMAGE_DPI`; the approximate token boxes; DOCX without boxes.
    - `teitok_conformance_plan.md` Stage 8 marked done.
    - The CONTRIBUTING release row; DEVLOG.

## Open questions

- Decision 1, (a) apportioned word boxes or (b) line boxes for every token: (a) is recommended.
- Should `/enrich` accept the record as the only input (deriving the text table from `lines[]` itself), so a client does not build the CSV? That is a separate, small change to `_normalize()`, worth its own issue once W5 works.

## Out of scope

- Word-level boxes from digital-convert. The record schema has no word level; pdfplumber's word boxes exist inside the converter, and exporting them would be a hub schema change.
- Page images for born-digital PDFs: rendering them is the client's or page-classification's business. `INPUT_PAGES_DIR` already consumes them.
