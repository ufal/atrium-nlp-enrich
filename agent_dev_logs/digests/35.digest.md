## 🎯 Goal
Factor VI wants stateless processes; factor VIII wants scale-out by replica. Four of five ATRIUM services satisfy both. `/jobs` in this repo does not, and the uniform reference manifest implies it does.

## 🔎 Verified state

**The registry is process-local.** `service/jobs.py:19`:

```python
_jobs: Dict[str, Job] = {}
_job_lock = asyncio.Lock()
```

`create_job()` inserts into that dict under the lock. It lives in the address space of one uvicorn process.

**So is the workspace.** `service/enrichment.py:39`:

```python
_API_JOBS_ROOT = Path(os.environ.get("API_JOBS_ROOT", _REPO_ROOT / "TEMP" / "api_jobs"))
```

Container-local disk by default, with no shared-volume assumption anywhere in the reference manifest.

**Consequence.** `GET /jobs/{id}` resolves only on the replica that accepted the `POST`. With `replicas: 2` behind a Service, a client polling its own job gets a 404 roughly half the time — for a job that is running correctly on the other pod. There is no error, no log line at fault, and nothing in the manifest that would lead an operator to the replica count.

**The contrast is sharp.** The other four services keep per-request scratch in a `tempfile.TemporaryDirectory()` that dies with the request — alto `service/text_api.py:424`, llm-enrich `service/api.py:467,501`, page-classification `document_json.py:117`, translator `service/api.py:146`. They are stateless by construction. This repo is the exception because `/jobs` is an async job API, which is a legitimate design that simply has a state requirement the others do not.

**Factor VIII is otherwise correct** across the ecosystem: one uvicorn process per container, no `--workers` anywhere, scale-out by replica. Batch-side parallelism is process-pool based and env-tunable. The replica model is right; this one endpoint is the only thing that makes it wrong here.

## 🔎 Why this is a handover problem, not just a design note

`docs/templates/k8s/atrium-service.deployment.yaml` in the hub is a **uniform** manifest, substituted per tool (`sed -e 's/<tool>/nlp-enrich/g' …`, per `docs/k8s_acceptance_runbook.md`). It carries one replica policy for all five services. So the document that tells ARÚP/ARÚB how to deploy this service implies it scales like the other four.

It does not. And the failure — an intermittent 404 on a job that exists — is close to undiagnosable from the outside.

## ⏳ Open
- **Which resolution.** The issue offers both without recommending: (1) document the constraint and set `replicas: 1` with a comment; (2) move the registry and workspace root to shared state. For a project in pre-closure architecture review with a fixed remaining lifetime, (1) is almost certainly right — but it has to be *stated*, and stated in three places (manifest, `k8s_deployment.md`, acceptance runbook), or it is not a resolution.
- **A uniform manifest with a per-tool exception needs a mechanism.** Setting `replicas: 1` "for nlp-enrich" in a file that is `sed`-substituted for all five means either a conditional the template cannot express, a second template, or a documented override step in the runbook. Nobody has said which, and this is the actual design work in the issue.
- **`API_KEEP_WORKSPACES` and job retention.** `service/enrichment.py:41` reads `API_KEEP_WORKSPACES`; with a container-local root, a kept workspace survives only as long as the pod. If option 1 is chosen, that variable's documented meaning should say so.
- **Relationship to [atrium-project#61](https://github.com/ufal/atrium-project/issues/61).** That issue asks what `<workspace>/out/processing.log` (`service/enrichment.py:234`) is for. The answer partly depends on this one: a per-job log on container-local disk is only meaningful if jobs are pinned to a pod and readable while it lives. Decide `/jobs`'s promise here; let #61 follow.
- **#55's drain contract must not regress.** `POST /jobs` registers with `ServiceState.track()`, which the graceful-shutdown drain awaits — the fix for "a rolling restart kills in-flight work". Any change to job storage has to keep that registration intact, and option 2 in particular touches exactly that code path.
