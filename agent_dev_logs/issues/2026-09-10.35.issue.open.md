# [\#35 Issue](https://github.com/ufal/atrium-nlp-enrich/issues/35) `open`: Processes and Concurrency: state or remove single-replica constraint for `/jobs`
**Labels**: `enhancement`, `development`


#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-09-10 12:24](https://github.com/ufal/atrium-nlp-enrich/issues/35):

Four of five services are properly stateless — per-request scratch lives in a `tempfile.TemporaryDirectory()` and dies with the request (alto `service/text_api.py:424`, llm `service/api.py:467,501`, pc `document_json.py:117`, translator `service/api.py:146`). One is not.

`atrium-nlp-enrich/service/jobs.py:19` holds a **process-local** registry:

```python
_jobs: Dict[str, Job] = {}
```

and `service/enrichment.py:39` writes workspaces under `API_JOBS_ROOT` (default `TEMP/api_jobs`, container-local disk). `GET /jobs/{id}` therefore only resolves on the replica that accepted the `POST` — a second replica returns 404 for a job that is running fine next door.

The replica model itself is right (one uvicorn process per container, no `--workers` anywhere; scale-out by replica). Factor VIII is undermined in exactly this one place, and **nothing says so**: `docs/templates/k8s/atrium-service.deployment.yaml` is a uniform manifest handed to ARÚP/ARÚB for all five services, which implies all five scale identically. One does not.

### Two honest resolutions — pick one

1. **Cheap**: document the constraint. Set `replicas: 1` explicitly in the manifest for nlp-enrich with a comment saying why, and state it in `docs/k8s_deployment.md`. This is probably right for the project's remaining lifetime.
2. **Correct**: move the job registry and workspace root to shared state, so `replicas > 1` behaves.

Either is fine. The current situation — an undocumented constraint under a uniform manifest — is not, because it fails as a 404 on a partner's cluster with no way to trace it back to a replica count.

### Acceptance

- Either `docs/k8s_deployment.md` states nlp-enrich's replica constraint and the manifest carries it, **or** a `POST /jobs` to one replica is retrievable by `GET /jobs/{id}` from another.
- If option 1: the constraint appears in the acceptance runbook too, so the partner does not discover it by scaling up.
- `#55`'s `ServiceState.track()` drain contract for in-flight jobs is unaffected either way — do not regress it.
